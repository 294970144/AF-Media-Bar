# AF Media Bar 性能优化计划

本计划覆盖新功能分支 `codex/performance-optimization` 的 WebView2 歌词、WPF 宿主与后台工作。每批以可测的资源和交互结果决定是否保留，不改变歌词、媒体、设置或任务栏的既有语义。

## 目标与测量口径

优先级依次为：全进程组的实际内存降低；待机 CPU/GPU 与周期唤醒尽量接近零且恢复迅速；WebView2 GPU 资源；活跃状态 CPU。工作集与私有提交量分别记录，不能把 `EmptyWorkingSet` 后的任务管理器读数当作真正释放。WebView2 的浏览器、渲染器和 GPU 子进程必须计入；GPU 利用率与专用/共享显存分开记录。

验收场景固定为单屏和双屏各一轮：无媒体启动、歌词关闭、无歌词媒体、播放逐字歌词、暂停、空闲 10 分钟、自动隐藏任务栏、锁屏/关屏后恢复、设置窗口开关、Explorer 重启、程序退出。每轮记录稳定后的内存/CPU/GPU/进程数、首次歌词呈现与恢复到正确帧的延迟分布；同一机器和配置上各重复三次。目标是无歌词待机的进程组私有提交量与空闲 CPU 明显低于未优化 `origin/main` 基线，显示关闭后 CPU/GPU 接近零，恢复不比基线出现可见的空白或卡顿。具体百分比和毫秒阈值在取得基线后确定。

## 第 0 批：基线与归因

1. 串行构建尚未优化的 `origin/main` Release 版作为 A/B 基线，记录提交、WebView2 Runtime、Windows/DPI/屏幕数与设置；后续每个批次用同一配置和脚本重复。不能把系统里其他应用的 `msedgewebview2.exe` 混进结果。
2. 增加仅供开发时运行的本地采样脚本，记录 AFMediaBar 与其 WebView2 进程树的 PID、启动时刻、工作集、私有提交量、CPU 时间增量、线程、句柄。用进程树和 WebView2 BrowserProcessId/进程信息核对归属与 PID 复用；GPU 利用率、专用/共享显存用任务管理器/Windows 性能工具采集。脚本不写入产品遥测或联网。
3. 对照已有 `[Prune]` 日志和 Performance/Memory 剖析，先识别持续增长、空转计时器、WebView2 进程及 WPF 缓存的实际贡献。

## 第 1 批：WebView2 生命周期与待机

1. 先设计并实现 `Ready`/`Unloaded`/`Dispose`/图形故障恢复的明确状态和一次性失败重试边界。当前 `Unloaded` 会释放渲染器，同一控件再次 `Loaded` 时却可能不再创建；修复并测试这条路径。渲染器中 fire-and-forget 的脚本发送与异步导航事件需要观察异常、代际检查，并保证释放后不发布结果。初始化失败必须向所有者可观察：现有 `InitializeAsync` 会自己捕获异常并返回，若外层仍以“未抛异常”判成功，可能留下 `renderer != null` 且永远 `IsReady=false` 的实例，后续也不会重试。
2. 在没有可用歌词或歌词功能关闭时避免创建 WebView2；保留元数据作为初始化中的呈现。参考但不直接移植 `origin/feat/mem-reduce`：其释放顺序、失败重试和图形故障恢复路径需重新设计。已有歌词到达时可在前奏期间预热。对已有 WebView2 采用短时隐藏保留、确定长时间无歌词后释放，避免切歌导致的反复创建。释放前先从视觉树摘除，再取消回调、计时器并 Dispose；保留 1×1 最小尺寸防护与当前故障恢复预算。该批单独做 A/B。
3. 在关屏、锁屏或任务栏不可见且 WebView 已就绪时，再实验 `TrySuspendAsync`/`Resume`。初始化期维持现有可见树条件；Ready 后须实际使控制器 `IsVisible=false`，不能以 WPF `Opacity=0` 代替。处理挂起返回 false、脚本仍在执行、自动恢复、异步期间状态反转。恢复时先 Resume、送最新样式和帧，再让歌词取代元数据。若此条件无法安全满足，可单独实验 `MemoryUsageTargetLevel.Low/Normal`，两套 API 不混用。
4. 单屏/双屏测量后再决定是否显式共享 `CoreWebView2Environment`；当前统一 User Data Folder 可能已有进程复用，不能凭控件数量推断进程数。只有实际剖析指出 JS/合成成本时，才继续调整 `Web/Lyrics` 的持续动画、`will-change`、布局读写或消息频率。保留硬件加速。

## 第 2 批：WPF、缓存与后台 CPU

1. 用分配和保留对象证据检查设置窗口、页面/ViewModel、位图、Popup/事件订阅。页面 ViewModel 当前是 DI 单例并订阅静态设置事件；任何改为 transient 或关窗释放的方案须先补可验证的退订与重建生命周期。
2. 列出 L0/L1/L2 的常驻计时器和工作项，按实际运行状态归因。L1 需要无媒体至少 5 分钟且用户空闲至少 10 分钟，L2 来自关屏或锁屏；已有剪枝会停掉多项计时器。优先让无媒体/不可见组件停止工作，而不是全局放慢可见交互。检查进度条、歌词 50 ms 投影、16 ms 跑马灯、WPF 频谱帧、任务栏定位/UIA、指标租约、音频端点扫描和更新排期；仅修改有测量收益的路径。
3. 若 GPU 剖析指向 WPF 合成，再测试 BlurEffect、透明层、频繁布局/几何写入的针对性削减，保持高对比度、DPI、多屏和 Explorer 恢复行为。GC `ConserveMemory`、发布参数只做独立 A/B；.NET 10 的 DATAS 默认行为需实测和官方口径核对，不盲目显式启用。

## 第 3 批：验收与交付

1. 每项优化单独记录改动前后、对应场景和回退条件；若内存下降以可感知的唤醒迟滞为代价，则撤销或调整。新纯策略覆盖会导致错误显示、泄漏或恢复失败的状态转换。
2. 按 `CONTRIBUTING.md` 串行运行 RID restore → Release build → `--no-build` test，运行架构扫描与 `git diff --check`。真实 Windows 桌面核对退出后无残留进程、重复启停资源不累积、单/双屏、任务栏自动隐藏、锁屏唤醒、Explorer 重启、逐字歌词和 WebView2 图形故障回退。没有覆盖的系统与播放器明确写“待维护者验收”。
3. 建立 `tasks/YYYY...` 实施报告，记录审查反馈、原始与汇总数据、测试失败及重跑、实施结果和未验证风险。更新相关功能文档与中英文 `[Unreleased]`（如果行为变化显著），不修改已发布版本或设置 schema。

## 审查要点

子智能体已在代码修改前独立审查并提出上述修订。特别保留“先懒创建和稳健生命周期、单独测收益，再实验挂起，最后按剖析结果优化 JS/GPU 与 WPF”的实施顺序。
